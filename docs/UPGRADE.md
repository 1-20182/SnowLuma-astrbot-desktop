# 升级指南

> 一句话：**程序文件会被替换，你的配置、装好的 SnowLuma / AstrBot、下载缓存都不会动。**
> 因为从 v1.1.0 起，数据与安装默认都在程序目录**之外**（`<非 C 盘>\SnowLumaAstrBot\{data,runtime,downloads}`）。

---

## 一、版本规则（先看这个）

| 位数 | 什么时候变 | 例子 |
| --- | --- | --- |
| 主版本 `X.0.0` | 有**不兼容**改动（配置格式、目录结构、对外接口） | 需要手动迁移 |
| 次版本 `1.X.0` | 加功能 | 直接升级，配置自动迁移 |
| 修订号 `1.0.X` | 修 bug / 文案 / 打包 | 直接升级 |

**兼容性承诺**

1. 配置字段**只增不删**；老配置在新版本里会自动迁移（迁移前留 `config.v…bak.json`）
2. 数据目录、安装目录、下载缓存的位置**不会因为升级而变化**
3. 同一主版本内可以**降级**（把旧 zip 再装一次即可）
4. 跨主版本升级前，先备份 `data` 目录

---

## 二、我该用哪种升级方式？

先确认你的数据在哪（配置页 →「安装位置与备份」看路径）：

| 你的情况 | 推荐方式 |
| --- | --- |
| 数据在 `D:\SnowLumaAstrBot\data`（程序目录外，默认） | 任意方式都可以，最省事是**应用内升级** |
| 数据在程序目录里（老版本/便携用法） | 用**应用内升级**（它会保留 `data`），或先迁数据再覆盖 |
| 只想尝鲜、不怕折腾 | 解压到**新目录**，把旧 `data` 拷过去（干净但不省空间） |

---

## 三、方式 A：应用内升级（推荐）

1. 下载新的发布 zip（**不要解压**）
2. 打开控制台 →「配置」→「升级控制台」
3. 点「选择…」挑这个 zip → 点「检查」
   - 会显示：升级包版本、当前版本、能不能装（比当前旧的需要强制）
4. 点「开始升级」，确认弹窗

之后程序会自己完成（约 10~30 秒）：

```
备份程序目录 → data\backups\program-v<旧版本>-<时间>\
程序退出      → 释放 exe/dll 占用
覆盖新版本    → robocopy /E（不删除 data、runtime、downloads）
启动新版本    → 自动打开
```

- 覆盖失败会自动**回滚**并启动旧版本
- 全过程日志：`data\upgrade\upgrade.log`
- 升级完成后可以在「配置」页确认版本号变了

> 桌面版会连窗口一起退出，属正常现象——由升级助手接管，不用手动点。

---

## 四、方式 B：手动覆盖（两步，别搞错顺序）

1. **先彻底退出程序**
   - 桌面版：右上角 `⏻` 长按 →「彻底退出」（**不要**只点最小化）
   - 浏览器版：顶栏「退出」，然后确认 `任务管理器` 里没有 `SnowLuma-AstrBot-Console.exe`
2. **解压新 zip 覆盖到原程序目录**（同一路径覆盖即可）

为什么顺序重要：Windows 不允许覆盖正在运行的 exe/dll，没退出就会报"文件被占用/无法写入"。

覆盖完检查：

- 程序目录里**不要**出现被覆盖掉的 `data` / `runtime`（如果你的 data 在程序目录里，覆盖前先把它挪出去）
- 打开后「配置」页的 QQ 号、API Key 还在 → 说明数据没丢

---

## 五、方式 C：数据在程序目录里怎么办

老版本可能把 `data`、`runtime` 放在程序旁边。两种做法：

**做法 1（推荐）**：用应用内升级，它会把 `data`、`runtime` 排除在覆盖范围外，原样保留。

**做法 2**：先搬家，再覆盖

1. 「配置」→「安装位置与备份」记下数据目录
2. 「部署 → 卸载与清理」没用的先删；或用资源管理器把 `data`、`runtime` 整个移动到 `D:\SnowLumaAstrBot\` 下
3. 设置环境变量指向新位置（或直接放到默认位置：
   `D:\SnowLumaAstrBot\data` 与 `D:\SnowLumaAstrBot\runtime`）
4. 启动新版本确认状态正常，再删旧的程序目录

---

## 六、升级前检查清单

- [ ] 机器人可以短暂停一下（升级会重启程序，服务会中断 10~30 秒）
- [ ] 磁盘剩余空间 ≥ 升级包大小的 3 倍（解压 + 备份）
- [ ] 记住当前版本号（「配置」页 / 顶栏）与数据目录路径
- [ ] 重要配置先「导出配置」（配置页按钮）留一份

---

## 七、回滚（升级后不对劲）

1. **程序回滚**：把 `data\backups\program-v<旧版本>-<时间>\` 里的文件拷回程序目录（先退出程序）
2. **还是不行**：重新下载旧版本 zip，走「方式 A/B」装回去（同主版本可降级）
3. **配置回滚**：找 `data\config.v<旧版本>.bak.<时间>.json`，改名成 `config.json`
4. 升级日志在 `data\upgrade\upgrade.log`，提 issue 时带上它

---

## 八、常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 覆盖时提示"文件被占用" | 还有进程没退（含后台 backend） | 任务管理器结束 `SnowLuma-AstrBot-Console.exe` / `SnowLuma-Desktop.exe` 后重试 |
| 升级后配置"变回默认" | 数据目录换了位置（比如换了盘） | 把旧 `data` 拷到新位置；或在配置页「导入配置」 |
| 升级后服务起不来 | 端口被旧进程占着 / 依赖缺失 | 配置页「检查并自动换端口」；看「运行」页日志 |
| 升级后 SnowLuma 不认原来的登录 | 安装目录被覆盖了 | 正常升级不会覆盖 `runtime`；若被覆盖，重新部署 + 重新扫码 |
| 应用内升级点了没反应 | 助手脚本被杀软拦了 | 看 `data\upgrade\upgrade.log`；改用「方式 B」手动覆盖 |

---

## 九、开发者：发布新版本时要做什么

1. 改代码 → `scripts\bump.ps1 patch|minor|major "说明"`（同步 `VERSION` / `package.json` / `CHANGELOG.md`）
2. 如果**新增了配置字段**：在 `slab/migrations.py` 里加一条迁移，并把 `CURRENT_CONFIG_VERSION` +1
3. 如果有**不兼容改动**：主版本 +1，并在 `CHANGELOG.md` 写清迁移步骤
4. 跑测试：`.venv\Scripts\python.exe -m pytest -o addopts="" -q`
5. 打包：`packaging\build-exe.bat` → `desktop\build.bat`（两者都会生成带版本号的 zip）
